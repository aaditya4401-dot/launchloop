# PLAN.md — Rocket Flight Planner & Analytics Platform

> Design notes for a system that generates realistic rocket-flight data, analyzes it,
> and uses a team of AI agents to **design** a launch that meets its mission constraints.
> It spans three domains I work across — **data engineering**, **data science**, and
> **multi-agent AI** — on a single self-generated rocketry dataset.
>
> This document captures the architecture and the reasoning behind each decision; the
> [README](README.md) is the walkthrough of the finished system.

---

## The idea in plain English

Real rocket launches produce a flood of sensor data, and a launch team has to decide:
*given today's rocket, motor, and weather — is it safe to fly, and can we hit our target?*

This project recreates that whole loop **on a laptop, with zero external data**:

1. **Simulate** thousands of flights with realistic randomness (wind, motor strength, mass vary each time).
2. **Store & organize** that messy output into clean, queryable tables.
3. **Learn from it** — predict how high the rocket goes, spot flights that went wrong.
4. **Design** — a team of AI agents proposes a rocket configuration, simulates it, and
   keeps adjusting it until it meets the mission's target and safety limits (or proves it can't).

Nothing is downloaded. All flight data is generated by a physics simulator called RocketPy,
so you own the entire pipeline end to end. Crucially, that same simulator becomes the
**oracle** in the final phase — the thing that tells the agents whether their design
actually works, instead of them just asserting that it does.

---

## Why I built it this way

Each layer is a real capability, exercised end to end rather than in isolation:

| Layer | What it exercises |
|---|---|
| Simulation + storage | Turning messy multi-run output into clean, queryable tables — **data engineering / pipelines** |
| Prediction + anomaly detection | Models that learn from the data and are validated against a held-out answer key — **data science / ML** |
| The agent design loop | Agents that act on an environment, verify against ground truth, and correct themselves — **multi-agent / agentic AI** |

The design principle that ties it together: the agents **design a flight and verify it
against a physics engine — they don't just describe one**. Most multi-agent projects fan
out, gather text, and write a report; this one closes a loop against ground truth, which is
both harder and more useful — the simulator, not the model's own say-so, decides whether a
design is flyable.

## The tech stack (what each thing is, and why it's here)

- **Python 3.13** — the language. (Avoid 3.14 for now; one optional mapping feature isn't ready there.)
- **RocketPy** — a rocket flight simulator. You describe a rocket + motor + weather, it computes the full flight. This is your data source *and* your oracle.
- **Parquet files** — a compact file format for tables (like a supercharged CSV). Each simulated flight gets saved as one.
- **DuckDB** — a database that runs inside your script (no server to set up). It reads your Parquet files and lets you query them with SQL.
- **dbt** — a tool for organizing SQL transformations into clean, documented steps. This is the one "named tool" recruiters scan for; keep your use of it small.
- **polars** — a fast library for working with tables in Python (like pandas, but quicker and cleaner).
- **scikit-learn** — the standard Python library for machine-learning models (prediction, anomaly detection).
- **LangGraph** — a framework for building AI agents that pass information between each other in a defined flow. This is your multi-agent layer.
- **Anthropic API (Claude)** — the "brain" each agent uses to reason. (You're already in this world.)
- **Typer + Makefile** — simple ways to run your project with one command (e.g. `make data`).

You install these as you reach the phase that needs them — not all at once.

## How the pieces connect (data flow)

```
RocketPy simulation
      │  (thousands of flights, each with random wind/motor/mass)
      ▼
Parquet files in data/raw/        ← one file per flight, full time-series
      │
      ▼
DuckDB + dbt                      ← clean, combine, make a one-row-per-flight summary
      │
      ├──────────────► scikit-learn models   (predict apogee, detect anomalies)
      │                        │
      ▼                        ▼
LangGraph agent team ──► propose a config ──► RocketPy verifies it (the oracle)
      ▲                                              │
      └───────── adjust and retry ◄──────────────────┘
      │  (loop until constraints met, or justified no-go)
      ▼
Verified flight design + report
```

The key difference from a typical agent project: the arrow **loops back**. Agents propose,
the simulator judges, agents correct. The report at the end is a byproduct of that loop,
not the point of it.

## Build it in three phases

Work top to bottom. Don't scaffold everything at once — get each phase producing
something real before moving on. Each phase says what to learn, what to build, and
how you know it's done.

### Phase 1 — Generate and store the data (data engineering)

**Goal:** produce thousands of simulated flights and land them in a queryable database.

**Build:**
- Define one rocket + motor + weather in RocketPy that produces a sensible flight.
- Use **fetch-free weather**: a `custom_atmosphere` with your own wind numbers. *Do not use the Ensemble/GEFS weather model — it downloads forecasts, which breaks the "no fetching" rule.*
- Run a loop that flies the rocket ~1,000 times, each time nudging wind, motor strength, and mass randomly. Save each flight's time-series (altitude, vertical speed, acceleration) as a Parquet file in `data/raw/`.
  - **Wind:** draw a direction `θ ~ uniform(0, 2π)` and a magnitude `m ~ uniform(0, 20)` m/s, then `wind_u = m·cosθ`, `wind_v = m·sinθ`. (Draw magnitude + direction, not two independent components, or the total won't be bounded.)
  - **Mass:** 14.4 kg ± ~5%, normal. **Motor strength:** scale the thrust curve ±8%, normal.
- Deliberately weaken the motor on ~10% of flights (scale thrust to 55–70%) and label them — these are your known "bad" flights for Phase 2. *(This band is easy to detect on purpose for now; tighten to ~75–85% later to make Phase 2 less trivial.)*
- Save the **actual continuous knob values** (wind magnitude, mass, thrust scale) as columns, not just the weak-motor boolean — they become features later.
- Seed **per flight** (`base_seed + flight_id`) so any single flight is reproducible on its own.
- **Smoke-test on ~5 flights first**, forcing one weak-motor flight in (a very weak motor barely clears the rail → the most likely thing to break), before running all 1,000.
- Load all the Parquet files into DuckDB, and use a couple of small **dbt** models to build one clean summary table: one row per flight with its apogee, max speed, and label.

**Done when:** `make data` rebuilds the whole database from scratch, and you can run a
SQL query in DuckDB that returns one row per flight.

### Phase 2 — Learn from the data (data science)

**Goal:** build models that predict and detect.

**Build:**
- **Apogee prediction:** using only the first few seconds of each flight as input, predict the final apogee, and report how close the prediction is. *(This model is reused in Phase 3 as a cheap pre-screen — so it's worth making decent.)*
- **Anomaly detection:** train a model to flag "bad" flights, and validate it against the weak-motor flights labeled in Phase 1 (the answer key).
- Save the charts to `notebooks/` for the README.

**Done when:** `make models` trains both, prints their accuracy, and correctly catches
most of the flights you sabotaged.

### Phase 3 — Closed-loop flight designer (multi-agent AI)

**Goal:** agents that don't just describe a flight — they *design* one. They change the
rocket configuration, re-simulate it in RocketPy, and iterate until it meets the mission's
constraints, or declare it infeasible with reasons.

**The reframe:** instead of "check this flight and report," the task is constraint
satisfaction: *given a mission (target apogee, a hard altitude ceiling from the launch
waiver, the day's wind, and a short menu of available motors), find a flyable
configuration — or a justified no-go.*

**The loop (this is the part that isn't report-writing):**
```
propose a configuration
      → evaluate(config) in RocketPy        ← the oracle
      → observe metrics (apogee, stability, rail-exit velocity, dispersion)
      → check against constraints
      → if violated: propose a corrective change, re-simulate
      → repeat until satisfied, or iteration budget is spent
```

**Why multiple agents actually earn their place here** (be honest about this): give the
specialists *competing* objectives, so the orchestrator arbitrates a real tradeoff instead
of stapling reports together:
- **Performance agent** — wants to hit the target apogee (push for a bigger motor, less ballast)
- **Safety agent** — wants stability margin and rail-exit velocity in the safe band, and apogee under the ceiling (smaller motor, more ballast) — *directly fights performance*
- **Recovery agent** — wants landing dispersion contained (parachute sizing, descent rate)
- **Orchestrator** — proposes the next change, breaks ties between the specialists, and calls go / no-go

Adding ballast for stability lowers apogee; a bigger motor for apogee can blow the ceiling
and cut stability. The agents genuinely pull in different directions — that's what makes
the multi-agent structure load-bearing rather than decorative.

**Constraints checked each iteration:**
- Apogee ≤ waiver ceiling — *hard*
- Stability margin ~1.5–2.5 calibers — *hard safety*
- Rail-exit velocity ≥ ~15–20 m/s — *hard safety* (the rail-clearance instability we hit in Phase 1)
- Apogee close to target — *objective to optimize toward*

**Corrective actions available to the agents:**
- add / remove ballast mass (moves apogee and stability)
- swap motor from the available menu (more / less impulse)
- adjust rail inclination (launch angle)
- resize parachute (recovery)

**Build:**
- Define the mission input (target apogee, ceiling, wind, motor menu).
- Wrap RocketPy as one `evaluate(config) → metrics` function — the oracle every agent calls.
- *Optional, and a nice touch:* use your Phase 2 apogee model as a **cheap pre-screen** —
  the ML model guesses whether a proposal is close before you spend a full simulation;
  RocketPy then verifies the survivors. Cheap proposer, expensive oracle.
- Build the LangGraph loop: propose → evaluate → check → correct, with a **hard cap on
  iterations** (e.g. 8 sims) so it can't spin forever or run up cost.
- Orchestrator emits the verdict: either the found configuration with its RocketPy-verified
  metrics, or a no-go naming the constraint it couldn't satisfy.
- A markdown report still gets written — but now it's a *byproduct* documenting what the
  system did and why, not the deliverable itself.

**Done when:** `make design TARGET=... CEILING=... WIND=...` takes a mission, runs real
RocketPy simulations in a loop, and either prints a verified flyable configuration or a
justified no-go — and you can watch the apogee move toward the target across iterations.

**Honesty note (keep this in mind):** even this could be done with one agent plus an
optimizer. The multi-agent structure is load-bearing *only because* the specialists hold
competing objectives and the orchestrator arbitrates them. If you ever collapse those
objectives into one, drop back to a single agent — don't keep agents around for decoration.

## Engineering constraints (the rules I held the build to)

- **Build phase by phase.** Phase 1 writes real Parquet files before any agent work begins.
- **Verify the RocketPy API against the installed version** (`pip show rocketpy`) before writing simulation code — its Monte Carlo / Stochastic module is still evolving, so method names and constructor arguments are checked against the local docs, not assumed. (Pinned to **1.12.1** — 1.13 was never published to PyPI.)
- **Two ways RocketPy gives data — use the right one:** the per-flight *time-series* (altitude/velocity over time) the Phase 2 models need is pulled from individual `Flight` objects in a manual loop; that loop feeds the dbt summary table. The built-in `MonteCarlo` class exports a dispersion *summary* across many flights — kept as a standalone study (`make dispersion`), not wired into `make data`.
- **Stay offline.** `custom_atmosphere` weather and inline motor/drag data (the PyPI wheel doesn't bundle RocketPy's example files). Nothing requires a download or API key except the LLM API in Phase 3.
- **In Phase 3, RocketPy is the oracle.** Every agent proposal is verified by an actual simulation before it's accepted — no agent asserts a metric the simulator didn't confirm. The loop's iterations are capped so cost stays bounded.
- **Keep dbt tiny** — 3-4 models, not a warehouse. It's there for signal, not scale.

## Glossary (one line each)

- **Apogee** — the highest point the rocket reaches.
- **Monte Carlo** — running the same simulation many times with random variation to see the range of outcomes.
- **Time-series** — a measurement recorded repeatedly over time (e.g. altitude every 0.01s).
- **Pipeline** — the automated path data takes from raw to clean-and-usable.
- **Anomaly detection** — automatically spotting data that looks abnormal.
- **Oracle** — a source of ground truth that tells you whether something actually works (here, the RocketPy simulator).
- **Closed loop** — act, observe the real result, correct, repeat — instead of producing output in one shot.
- **Stability margin** — how strongly a rocket resists tumbling, measured in calibers; too low is unstable, too high is over-stable and wind-sensitive.
- **Rail-exit velocity** — how fast the rocket is going as it leaves the launch rail; too slow and it's unstable before its fins bite.
- **Agent** — a small program that uses an LLM to reason about one focused task.
- **Orchestrator** — the agent that coordinates the others and makes the final call.
